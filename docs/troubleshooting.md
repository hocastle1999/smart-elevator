## 2026-11-08 실험 결과를 파일로 저장하자 한글이 깨짐

**문제**: 비교 실험 스크립트의 출력을 `> results.md`로 파일에 저장하자 한글이 모두 깨졌다. 화면에 바로 출력할 때는 멀쩡했다.

**원인**: Windows에서 Python은 표준 출력이 콘솔이 아니라 파일·파이프로 갈 때 시스템 기본 인코딩(한국어 Windows는 cp949)으로 쓴다. 이 프로젝트의 문서는 UTF-8이라 cp949 바이트가 UTF-8로 읽히며 깨졌다.

**해결**: 스크립트에 `--output` 옵션을 추가해 파일을 `encoding="utf-8"`로 직접 쓰게 했다(`scripts/compare_strategies.py`). 다시 돌린 결과의 숫자가 처음 실행과 똑같았다. 엔진이 결정적이라 실험이 재현된다는 확인도 겸했다.

**배운 점**:

- 셸 리디렉션(`>`)의 인코딩은 셸과 OS에 달려 있다. 사람이 읽을 결과 파일은 프로그램이 인코딩을 명시해 직접 쓴다.
- `open()`에 `encoding`을 빼면 같은 문제가 생긴다. 파일을 열 때는 항상 인코딩을 쓴다. (`PYTHONUTF8=1` 환경 변수로 전체를 UTF-8로 바꾸는 방법도 있지만, 실행하는 사람마다 설정해야 한다.)

## 2026-11-08 목적층 예약 방식이 같은 목적층 승객을 다른 카에 나눠 태움

**문제**: 1층에서 9층으로 가는 승객 두 명이 동시에 도착하면 같은 카에 모여야 하는데(목적층 예약의 핵심), 테스트에서 두 번째 승객이 빈 2번 카에 배정됐다.

**원인**: 비용 계산에서 "새로 생기는 정지 수"를 셀 때, 출발층(1층)이 이미 계획된 정지인지 카의 홀 호출로 확인했다. 그런데 첫 승객을 배정받은 카는 1층에 서 있었으므로 곧바로 문을 열었고, 엔진은 **문을 열 때 홀 호출을 지운다**. 그래서 이미 1층에서 문을 열고 있는데도 1층 정지를 새 정지로 세어 비용이 5초 × 1명만큼 올라갔다. 빈 카(비용 0)가 이겼다.

**해결**: 카가 문 상태(열림 중, 열림, 닫힘 중)이면 지금 층을 계획된 정지에 넣었다(`DestinationDispatch.select`). `test_destination_dispatch_groups_same_destination`이 이 경우를 확인한다.

**배운 점**:

- 전략은 엔진의 내부 규칙(호출을 언제 지우는가)에 기대어 판단한다. 엔진의 "문을 열 때 호출을 지운다"는 1단계 결정이 4단계 전략의 버그로 이어졌다. 상태를 읽어 판단하는 코드는 그 상태가 언제 바뀌는지까지 알아야 한다.
- 전체 실험만 돌렸다면 "목적층 예약이 생각보다 별로"라는 잘못된 결론을 냈을 것이다. 핵심 동작(같은 목적층 묶기)을 작은 시나리오 테스트로 먼저 확인해야 실험 결과를 믿을 수 있다.

## 2026-11-08 TestClient를 쓰자 httpx deprecation 경고가 남

**문제**: API 테스트에 FastAPI `TestClient`를 쓰자 테스트는 통과했지만 아래 경고가 나왔다. 1번 프로젝트와 같은 `httpx==0.28.1`을 그대로 가져온 상태였다.

```
StarletteDeprecationWarning: Using `httpx` with `starlette.testclient` is deprecated; install `httpx2` instead.
```

**원인**: FastAPI 0.162가 쓰는 Starlette 1.10부터 테스트 클라이언트가 `httpx2`를 먼저 찾고, 없으면 `httpx`로 대신하면서 경고를 낸다(`starlette/testclient.py`).

**해결**: `httpx` 대신 `httpx2==2.16.0`을 개발 의존성에 고정했다. 처음 보는 패키지라 설치 전에 PyPI 메타데이터를 확인했다. httpx 원작자가 만들고 pydantic 조직이 관리하는 후속 패키지다. 바꾼 뒤 경고 없이 148개 테스트가 통과했다.

**배운 점**:

- 경고는 다음 버전에서 오류가 된다는 예고다. 테스트가 통과해도 경고를 읽고 바로 처리한다.
- 다른 프로젝트의 의존성 목록을 복사할 때는 프레임워크 버전에 따라 짝이 되는 라이브러리가 바뀌었는지 확인한다.
- 이름이 비슷한 새 패키지(`httpx` → `httpx2`)는 타이포스쿼팅일 수 있다. 공식 문서나 프레임워크 코드가 그 이름을 가리키는지, 관리 주체가 누구인지 확인하고 설치한다.

## 2026-11-08 ruff format --check가 README.md 때문에 실패함

**문제**: 파이썬 코드는 모두 포맷돼 있는데 `ruff format --check .`가 `README.md`를 "다시 포맷해야 함"으로 보고하며 실패했다. 이대로 push했다면 CI의 Format check 단계가 실패했을 것이다.

```
unformatted: File would be reformatted
  --> README.md:41:24
```

**원인**: 사용 중인 ruff 0.17은 Markdown 파일 안의 ```` ```python ```` 코드 블록도 포맷 대상에 넣는다. README 예제에서 주석을 맞추려고 넣은 공백 정렬이 ruff 스타일(주석 앞 공백 2칸)과 달랐다. 1번 프로젝트의 README에는 파이썬 코드 블록이 없어서 겪지 못했다.

**해결**: `ruff format README.md`로 코드 블록을 ruff 스타일에 맞췄다. 문서의 코드 예제도 코드와 같은 규칙을 따르는 편이 낫다고 보고, 검사 대상에서 빼지 않았다.

**배운 점**:

- 도구의 검사 범위는 버전에 따라 넓어진다. "파이썬 파일만 검사하겠지"라고 가정하지 말고 문서를 고친 뒤에도 `ruff format --check .`를 돌린다.
- 문서 속 예제 코드도 실행해 출력이 설명과 맞는지 확인했다(README 예제의 정지 순서 6층 → 4층).
